### 1.2 ახალი შესაძლებლობები

* **OIDC ავთენტიფიკაცია** (`security/auth.py`) — JWT-ის შემოწმება IdP-ის JWKS-ით (მხოლოდ ასიმეტრიული
  ალგორითმები), `iss/aud/exp/iat/sub`; სურვილისამებრ MFA owner/accountant-ისთვის. როლი ყოველთვის DB-დან
  (`tenant_members`, RLS). `dev_headers` რეჟიმი `APP_ENV≠dev`-ზე გაშვებას არ იძლევა.
* **LLM გასაღების სასიცოცხლო ციკლი** — `POST /v1/llm/credentials/{id}/default`,
  `DELETE /v1/llm/credentials/{id}` (crypto-shredding: შიფრტექსტი იშლება). პირველი გასაღები ავტომატურად
  ნაგულისხმევია; სხვა პროვაიდერი ავტომატურად **არ** ხდება ნაგულისხმევი (თანხმობის გარეშე მონაცემები სხვა
  პროვაიდერთან არ უნდა წავიდეს).
* **`audit_log_verify(tenant)`** — ჯაჭვის შემოწმება SQL-ით.
* **`/ready`** — readiness probe (PostgreSQL + Redis); `/health` — liveness.
* **CI:** ცალკე `ruff` job, pip cache, `permissions: contents: read`.

## 2. რეკომენდაციები — რა იქნება უკეთესი

პრიორიტეტი: **P0** — production-მდე აუცილებელი; **P1** — პირველ თვეებში; **P2** — ზრდისთვის.

### P0 — production-მდე

1. **თანხმობების აღსრულება კოდში.** `consents` ცხრილი არსებობს, მაგრამ კოდი მას არსად ამოწმებს.
   LLM-ზე დოკუმენტის გაგზავნამდე უნდა მოწმდებოდეს აქტიური `ai_processing` (პერსონალური მონაცემების
   საზღვარგარეთ გადაცემა), fallback-მდე — `llm_fallback_other_provider`, rs.ge-ზე მოქმედებამდე —
   `rsge_automation_mandate`. თანხმობის ტექსტის ვერსიები იურისტმა უნდა განსაზღვროს.
2. **მიგრაციები.** `schema.sql` მხოლოდ ცარიელ ბაზაზე ეშვება. პირველ deploy-მდე — Alembic (ან sqitch /
   ნუმერირებული SQL + runner) და CI-ში „ცარიელი ბაზა → ყველა მიგრაცია → ტესტები“.
3. **მძიმე ოპერაციები რიგში.** `/v1/documents/extract` LLM-ს API პროცესში ელოდება (შეიძლება წუთები
   დასჭირდეს). საჭიროა: ფაილი → S3 → `documents` → დავალება რიგში (ARQ/Celery; შემდეგ Temporal) →
   `llm_calls` ჩანაწერი (ტოკენები/ხარჯი) → `document_extractions`. ამავე ფენაში — rate limit tenant-ზე.
4. **დაზუსტებული დეკლარაცია.** `declarations_one_active_per_period` და წარდგენილი დეკლარაციის
   უცვლელობა ნიშნავს, რომ შესწორებისთვის მოდელი ჯერ არ არის. საჭიროა `revision` /
   `amends_declaration_id` სვეტი და უნიკალურობა `(taxpayer_id, type, period_start, revision)`-ზე.
5. **საგადასახადო წესების დადასტურება ბუღალტერთან** — განსაკუთრებით `ZERO_ACTIVITY_POLICY`: მოგების
   და წყაროსთან დაკავებული საშემოსავლო გადასახადის ნულოვანი დეკლარაცია სავალდებულოა თუ `NOT_REQUIRED`
   (ობიექტის/გაცემის არარსებობისას), და მცირე ბიზნესის დეკლარაციის სიხშირე (ყოველთვიური თუ წლიური).
6. **rs.ge სელექტორები და SOAP სიგნატურები** — `playwright codegen` ავტორიზებული ანგარიშით; WSDL-ით
   გადამოწმება (უცვლელად რჩება README-ის სიიდან).
7. **IdP-ის კონფიგურაცია** — Keycloak/Auth0: MFA owner/accountant-ისთვის, `users.auth_subject`-ის
   შევსება რეგისტრაციისას (ცალკე, პრივილეგირებული სერვისით), `APP_AUTH_MODE=oidc`.

### P1 — სტაბილურობა, უსაფრთხოება, ხარჯი

8. **audit ჯაჭვის „დაჭედება“ (anchoring).** ჯაჭვი ვერ აჩენს *ბოლო* ჩანაწერების წაშლას. დღეში ერთხელ
   `audit_log_verify(...).last_hash` → S3 Object Lock (WORM); შემოწმება — ამ ჰეშამდე.
9. **ცალკე DB როლები.** დადასტურების guard `app.actor_type`-ს ენდობა, რომელსაც აპლიკაცია აყენებს.
   ძლიერი დაცვა: worker-ის როლს `approved_*` სვეტებზე `UPDATE` უფლება არ ჰქონდეს (column-level GRANT),
   დადასტურებას წერდეს მხოლოდ API-ის როლი.
10. **LLM-ის ხარჯის ოპტიმიზაცია.**
    * თვის 3–7 დღის დოკუმენტების დამუშავება დროში არ არის კრიტიკული → **Batch API** (Claude / OpenAI /
      Gemini — სამივეს აქვს, ≈50% იაფი).
    * tenant-ის ანგარიშთა გეგმა + system prompt სტაბილური prefix-ია → **prompt caching** (Claude —
      `cache_control`; OpenAI/Gemini — ავტომატური/იმპლიციტური). რეალური ანგარიშთა გეგმა ასობით
      სტრიქონია, ამიტომ ეკონომია მნიშვნელოვანია.
    * ცნობილი ბანკების (TBC, BOG) ამონაწერებისთვის **დეტერმინისტული პარსერი** — LLM საერთოდ არ სჭირდება.
11. **Eval ნაკრები და რეგრესიის კონტროლი.** `document_extractions.corrections` (ბუღალტრის შესწორებები)
    → ანონიმიზებული eval ნაკრები; ყოველ prompt/მოდელის ცვლილებაზე სიზუსტე პროვაიდერების მიხედვით;
    UI-ში მოდელის რეკომენდაცია ამ მონაცემებით.
12. **დაკვირვებადობა.** OpenTelemetry (trace: API → worker → LLM/rs.ge), Sentry (PII scrubbing —
    `redact()` იგივე წესებით), მეტრიკები: LLM შეცდომები/latency/ხარჯი პროვაიდერზე, rs.ge canary.
13. **მიწოდების ჯაჭვი.** lock-ფაილი (`uv lock` / pip-tools) რეპროდუცირებადი build-ისთვის, Renovate /
    Dependabot, `pip-audit` და image-ის სკანირება (Trivy) CI-ში, ტიპების შემოწმება (mypy/pyright).
14. **API-ის ჰიგიენა frontend-მდე:** CORS მხოლოდ საკუთარ დომენზე, security headers, request size
    limit reverse proxy-ზე, rate limiting (მაგ. OTP endpoint-ზე).

### P2 — პროდუქტი და ზრდა

15. **სურათები:** HEIC (iPhone-ის ფოტოები ჩეკებზე) → JPEG, ავტომატური შემობრუნება/შეკუმშვა — ნაკლები
    ტოკენი და უკეთესი ამოცნობა.
16. **სელექტორები DB/YAML-ში** — rs.ge-ს ინტერფეისის ცვლილებაზე deploy არ დასჭირდეს; canary ამოწმებს.
17. **შეხსენებები და OTP მიწოდება** — Telegram bot / push; `reminders` ცხრილის scheduler.
18. **ბუღალტრული ფირმის dashboard** — ბევრი კლიენტი ერთ ეკრანზე, ვადების „წითელი ზონა“, მასობრივი
    დადასტურება (roadmap v2).
19. **ოფიციალური ინტეგრაცია შემოსავლების სამსახურთან** — ბრაუზერის ავტომატიზაცია დროებითი ხიდია.
20. **„Managed key“ tier** — BYOK-ის პარალელურად, მომხმარებლისთვის, ვისაც საკუთარი LLM ანგარიში არ აქვს.

## 3. რა ვერ შემოწმდა ამ სესიაში

* **Docker image-ის build** — Docker Hub-მა დააბრუნა `429 Too Many Requests`. Dockerfile-ის ორფაზიანი
  ინსტალაცია შემოწმდა ცალკე (pip), `PLAYWRIGHT_BROWSERS_PATH` Playwright-ის სტანდარტული მექანიზმია;
  პირველი build CI-ში/ლოკალურად მაინც გადაამოწმეთ.
* **ნამდვილი LLM API-ები და eservice.rs.ge** — ტესტები იყენებს ნამდვილ SDK-ებს HTTP mock-ით და ყალბ
  პორტალს (როგორც ადრე).
* **არსებული ბაზის მიგრაცია** — `schema.sql` შეიცვალა (`audit_log.seq`, ახალი ტრიგერები). თუ სადმე უკვე
  არსებობს ბაზა ძველი სქემით, საჭიროა ხელით მიგრაცია (იხ. P0 #2).
